event-ticketing-platform — capstone

Event, Search & Booking Services

What Phase 3 built, and what Phase 8 measured on top of it. Booking Service provisions Ticket rows idempotently from Event Service's Kafka payload (integration point #2), and books a specific seat through one of two independently swappable hold mechanisms behind a single TicketHoldStrategy interface — a cron sweep over a Postgres column, or a self-expiring Redis SET NX EX lock — selected by one config value, never branched on in code. Both proven correct in Phase 3 (25 simulated clients racing one seat, exactly one wins, under each mechanism) and, as of Phase 8, both measured under a fixed 300-request contention burst, three runs per strategy: hold-acquisition and passive-release latency turned out statistically indistinguishable between strategies at this scale, with only immediate-release trigger time showing a small, consistent edge for cron (see §07 below and the Feature Development Process report chapter for the full analysis, including a real measurement bug a dedicated review caught and fixed along the way). Also closed a gap left open since Phase 1: DELETE /events/{id} now refuses a PUBLISHED event outright, since Event Service has no channel to check Booking Service for live bookings. Traced 2026-08-16 (Phase 3 sections), updated 2026-08-16 (Phase 8 benchmark).

01 — Topology

One entrypoint, three services — Kafka now fans out to two independent consumers

Traefik routes to three services: event-service on its original catch-all label, search-service on PathPrefix(/search), booking-service on PathPrefix(/bookings) — both more-specific rules outrank the catch-all by rule length, no explicit priority needed. Publishing an event triggers Kafka integration point #2 — booking-service runs a second, independent consumer group against the same event.events topic, provisioning Ticket rows idempotently. Redis backs one of Booking Service's two swappable hold mechanisms. Phase 8 addition, not pictured below (on-demand only, not part of the always-on topology): a benchmark-profiled prometheus+grafana pair (make bench-up/make bench-down), scraping every service's existing /metrics endpoint — see infra/README.md for the profile and /benchmark for the standalone Python load harness that drove the numbers in §08.

02 — Auth flow

Same token, two outcomes — now on a real write route

This is the actual sequence from the walkthrough above, now run against POST /events instead of the Phase 0 demo route: alice (role user) gets turned away; bob (roles user+organizer) gets through and creates an event. Role alone isn't the whole story this phase — see the ownership note below the diagram.

Role alone stops here — it doesn't answer "whose event is this?" That's a second, explicit check in EventManager: on PATCH/DELETE /events/{id}, the stored organizer_id is compared against the caller's JWT subject before any mutation. Verified live: carol (organizer role, different subject) → 403 on both bob's event; bob → 200 on PATCH, 204 on DELETE of a still-DRAFT event of his own — a PUBLISHED event now returns 409 to its own owner too, regardless of ownership — a Phase 3 rule (decisions-log §15 amendment): Event Service has no channel to check Booking Service for live bookings, so deletion of a published event is refused outright rather than conditionally. The POST /events/{id}/publish route is guarded the identical role-plus-ownership way — not shown as a separate diagram since the mechanism is unchanged, only the route.

03 — Kafka integration point #1: publish → search

Event-carried state transfer, idempotent both ways

The first of five locked Kafka integration points (§7). No synchronous call from either service into the other — Event Service publishes a self-contained message (full seat list included, not a venue reference), Search Service consumes it whenever it gets to it. The gap in between is the eventual-consistency window (§7/§26): real, bounded, and tested, not hidden. Current-state note (Phase 3): the redelivered-DELETED-message flow below was true and tested when this diagram was traced (Phase 2, deleting a published event was allowed); as of Phase 3, EventProducer.publish_deleted no longer exists at all — a PUBLISHED event can never be deleted (§02) — so no code path in this system produces a DELETED message anymore. Search Service's consumer still handles one defensively (still real, still tested via a hand-replayed message, same as originally), it's just no longer reachable through any actual application flow.

04 — Kafka integration point #2: publish → ticket provisioning

The same message, a second independent consumer, a structurally idempotent write

The identical event.events message from §03 is also read by booking-service's own consumer group — a second, wholly independent subscriber to the same topic, not a fan-out event-service has to know about. Idempotency here isn't a checked condition the way it was for the Elasticsearch upsert-by-ID (§03): it's a property of one SQL statement shape plus a unique constraint, so there's no "have I seen this before" branch that could itself have a bug.

05 — Dual hold strategy: the booking-flow race, and how each mechanism wins it

One interface, two atomicity mechanisms, the identical guarantee

This is the report's centerpiece correctness claim, and the one thing in this codebase that genuinely branches at runtime (TicketHoldStrategy, §6) — everywhere else in this system is single-path. HOLD_STRATEGY picks which mechanism runs; neither BookingManager nor this diagram's outcome changes depending on which.

cron strategy

  • ✓ lock is tickets.status/hold_expires_at
  • ✓ one atomic conditional UPDATE ... WHERE status='available'
  • ✓ abandoned holds released by an APScheduler sweep, on an interval
  • ✓ sweep also expires the associated PENDING booking
  • ✓ 20/20 concurrent-acquire test runs: exactly one winner, repeated

redis strategy

  • ✓ lock is a Redis key — tickets.status is never touched
  • ✓ one atomic SET key value NX EX ttl
  • ✓ the Redis lock expires on its own — no sweep needed for that half
  • ✓ the PENDING Booking row still needs a sweep — age-based, its own APScheduler job
  • – documented trade-off: Postgres can't answer "is this held" here
  • ✓ 20/20 concurrent-acquire test runs: exactly one winner, repeated

07 — Hold-Mechanism Benchmark (Phase 8, measured)

Same 300-request contention burst, three runs per strategy — a genuinely mixed result

Fixed load profile, identical both strategies, repeated 3x each: a fresh 30-seat pool provisioned per run via the real API, 10 concurrent clients racing each seat (300 total requests), burst ramp (asyncio.gather, no ramp-up). Numbers below are mean (range) across the three runs. Full methodology, raw archived output, and the honest read of what does and doesn't distinguish the two strategies — including a real measurement bug (an HTTP client connection-pool cap silently throttling the burst) a dedicated adversarial review caught and fixed along the way — live in the Feature Development Process report chapter and docs/benchmark-results/.

cron

  • ✓ 30/30 successful bookings, 270/270 correctly rejected (409), all 3 runs
  • ✓ hold-acquisition latency: p50 0.431s (0.267–0.524) · p95 1.052s (0.731–1.233)
  • ✓ passive release latency (abandon → sweep): 12.07s (11.07–13.08)
  • ✓ immediate-release trigger (§17, simulated): 4.28ms (3.58–4.89)

redis

  • ✓ 30/30 successful bookings, 270/270 correctly rejected (409), all 3 runs
  • ✓ hold-acquisition latency: p50 0.446s (0.279–0.702) · p95 1.257s (1.074–1.559)
  • ✓ passive release latency (abandon → TTL/sweep): 12.73s (11.05–14.07)
  • ✓ immediate-release trigger (§17, simulated): 6.69ms (4.87–8.42)

Both strategies allocated the pool exactly correctly, every run — the same guarantee P3.T7 already proved at 25-client scale, reconfirmed here at 300, six times over. Hold-acquisition p50 and passive-release latency are statistically indistinguishable between strategies at this scale — the ranges overlap almost entirely, and the means differ by less than either strategy's own run-to-run variance. The one metric that showed a consistent gap in all three runs is immediate-release trigger time, where redis was slower every time (plausibly the same extra network hop to a separate Redis container), though the absolute gap is a few milliseconds either way, dwarfed by the ~12-second passive path both strategies share. An earlier single-run version of this benchmark reported cron winning cleanly on every metric — a second and third run didn't reproduce that acquisition-latency "win," which is itself the point: a single sample can look like a clean result purely by chance, and the fix wasn't a better story, it was more data.

08 — Reproduce this yourself

Every command below is real — this is exactly what was run to trace the diagrams above. Takes a couple of minutes.

# from repo root
make up                                    # boots all 12 containers
make seed                                  # baseline venues/performers/events + one seat map

# public read — hits real postgres, paged + sorted
curl "localhost/events?limit=2&sort_order=desc"
{"items":[...], "total":3, "limit":2, "offset":0}   200

# alice: user only — cannot create
TOKEN=$(./get-token.sh alice)
curl -X POST localhost/events -H "Authorization: Bearer $TOKEN" ...
{"detail":"Requires role: organizer"}              403

# bob: user + organizer — creates an event he owns
TOKEN=$(./get-token.sh bob)
curl -X POST localhost/events -H "Authorization: Bearer $TOKEN" ...
{"id":"...", "organizer_id":"<bob's sub>", ...}  201

# carol: organizer, but not the owner — blocked from bob's event
TOKEN=$(./get-token.sh carol)
curl -X PATCH localhost/events/<bob's event id> -H "Authorization: Bearer $TOKEN" ...
{"detail":"not the owning organizer"}             403

# bob attaches a seat map over HTTP — no seed script, no manual Mongo write
curl -X PUT localhost/events/<bob's event id>/seat-map -H "Authorization: Bearer $TOKEN" \
  -d '{"sections":[{"name":"A","rows":[{"name":"1","seats":[{"label":"A1","x":0,"y":0}]}]}]}'
{"event_id":"...", "sections":[...]}               200

# bob publishes his event — this is what triggers the Kafka message
curl -X POST localhost/events/<bob's event id>/publish -H "Authorization: Bearer $TOKEN"
{"status":"published", ...}                        200

# eventual-consistency window: not there immediately...
curl "localhost/search?q=<title words>"
{"items":[], "total":0, ...}                       200

# ...found once search-service's consumer catches up (sub-second locally)
curl "localhost/search?q=<title words>"
{"items":[{...}], "total":1, ...}                  200

# ...and provisioned into booking_db too (Kafka #2), same publish, same message
docker exec -it postgres psql -U booking_service -d booking_db \
  -c "SELECT id, status FROM tickets WHERE event_id = '<bob's event id>';"
available — one row per seat in the seat map above

# alice books the seat — no organizer role required, unlike every Event Service write
TOKEN=$(./get-token.sh alice)
curl -X POST localhost/bookings -H "Authorization: Bearer $TOKEN" \
  -d '{"ticket_id":"<the ticket id above>"}'
{"id":"...", "status":"pending", "ticket_id":"...", ...}  201

# bob tries to book the same seat right after — the race, under HOLD_STRATEGY=cron
TOKEN=$(./get-token.sh bob)
curl -X POST localhost/bookings -H "Authorization: Bearer $TOKEN" \
  -d '{"ticket_id":"<the same ticket id>"}'
{"detail":"seat unavailable"}                       409

# flip to the other strategy and repeat — same outcome, different mechanism
# (infra/docker-compose.yml: HOLD_STRATEGY: redis, then `docker compose up -d booking-service`)
same 201 / 409 split — verified live under both strategies

# bob tries to delete his now-published event — refused outright (§15 amendment)
curl -X DELETE localhost/events/<bob's event id> -H "Authorization: Bearer $TOKEN"
{"detail":"cannot delete a published event"}          409
