01 — Topology

One entrypoint, one service — now with two databases behind it

Traefik now routes to two services: event-service still on its original catch-all label, search-service on a specific PathPrefix(/search) that outranks it by rule length. What changed this phase: event-service publishes a keyed Kafka message when an event is published, updated while published, or deleted; search-service consumes it into Elasticsearch, idempotently, and serves GET /search. Redis is still provisioned but idle.

02 — Auth flow

Same token, two outcomes — now on a real write route

This is the actual sequence from the walkthrough above, now run against POST /events instead of the Phase 0 demo route: alice (role user) gets turned away; bob (roles user+organizer) gets through and creates an event. Role alone isn't the whole story this phase — see the ownership note below the diagram.

Role alone stops here — it doesn't answer "whose event is this?" That's a second, explicit check in EventManager: on PATCH/DELETE /events/{id}, the stored organizer_id is compared against the caller's JWT subject before any mutation. Verified live: carol (organizer role, different subject) → 403 on both bob's event; bob → 200/204 on his own. The new POST /events/{id}/publish route this phase is guarded the identical way — organizer role plus ownership — not shown as a separate diagram since the mechanism is unchanged, only the route.

03 — Kafka integration point #1: publish → search

Event-carried state transfer, idempotent both ways

The first of five locked Kafka integration points (§7). No synchronous call from either service into the other — Event Service publishes a self-contained message (full seat list included, not a venue reference), Search Service consumes it whenever it gets to it. The gap in between is the eventual-consistency window (§7/§26): real, bounded, and tested, not hidden.

05 — Reproduce this yourself

Every command below is real — this is exactly what was run to trace the diagrams above. Takes about a minute.

# from repo root
make up                                    # boots all 9 containers
make seed                                  # baseline venues/performers/events + one seat map

# public read — hits real postgres, paged + sorted
curl "localhost/events?limit=2&sort_order=desc"
{"items":[...], "total":3, "limit":2, "offset":0}   200

# alice: user only — cannot create
TOKEN=$(./get-token.sh alice)
curl -X POST localhost/events -H "Authorization: Bearer $TOKEN" ...
{"detail":"Requires role: organizer"}              403

# bob: user + organizer — creates an event he owns
TOKEN=$(./get-token.sh bob)
curl -X POST localhost/events -H "Authorization: Bearer $TOKEN" ...
{"id":"...", "organizer_id":"<bob's sub>", ...}  201

# carol: organizer, but not the owner — blocked from bob's event
TOKEN=$(./get-token.sh carol)
curl -X PATCH localhost/events/<bob's event id> -H "Authorization: Bearer $TOKEN" ...
{"detail":"not the owning organizer"}             403

# bob publishes his event — this is what triggers the Kafka message
curl -X POST localhost/events/<bob's event id>/publish -H "Authorization: Bearer $TOKEN"
{"status":"published", ...}                        200

# eventual-consistency window: not there immediately...
curl "localhost/search?q=<title words>"
{"items":[], "total":0, ...}                       200

# ...found once search-service's consumer catches up (sub-second locally)
curl "localhost/search?q=<title words>"
{"items":[{...}], "total":1, ...}                  200

make down                                  # tear down
